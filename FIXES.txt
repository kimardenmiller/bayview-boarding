  Fixed a real, reported bug: "can't go back and edit check-in date."
  Root cause: todayISO() computed "today" via
  `new Date().toISOString().slice(0,10)`, which is always UTC. In the
  evening Pacific time (after ~5pm PDT / 4pm PST), UTC has already
  rolled to tomorrow, so the app's own idea of "today" would be a full
  calendar day ahead of the user's actual local today - making today's
  real date (and the date input's min) reject it as "in the past",
  exactly when someone would go back to fix a date in the evening.

  calendar fields, not UTC) instead. Applied the same fix server-side in
  submit-booking's own todayISO, going one step further there: since the
  server has no timezone of its own, it now derives "today" from the
  client's own timezone (already captured as clientTimezone on every
  booking) via Intl.DateTimeFormat, falling back to UTC only if that's
  missing or invalid - otherwise the server-side backstop would have had
  the exact same bug, just moved from the browser to the server.
