- Sept 15, 2026: Booking flow refinements on top of the dog-profiles reorg.
  Vet and "Number of Dogs" moved from the (now per-dog) dog page to the
  owner page, asked once alongside name/phone/email; the returning-client
  "Look up" button there now also autofills the vet and every known dog
  (previously this lived in an automatic on-mount effect on the dog page -

  page). Each dog now gets its own page titled "Dog 1", "Dog 2", etc.
  instead of all dogs stacked on one page - Progress/step count are
  computed dynamically from the dog count (Owner + N dog pages + Dates +
  Agreement + Sign). Vet placeholder text changed to "Select a Vet".
  Aggression/health questions were already required to advance past a dog
  page but showed no message if left blank (the Field wasn't passed an
  error prop) - fixed, they now warn "Please select an answer" like every
  other required field. Bookings can no longer be made for a check-in date
  in the past - validated both client-side (StepDates, the date input's
  min attribute is only a UI hint) and server-side in submit-booking
  (the actual boundary, since anon has no direct table access at all).
  Database cleared of all records (including stays_legacy) per request -
  the 3 backfilled owners/dogs/9 stays were test data, not real bookings.
  Tests: App.test.js helpers rewritten for the per-dog-page flow (6 new/
  rewritten tests covering vet default text, the Dog-2 page, aggression/
  health warnings independently and together, past-date rejection, a
  2-dog submission's payload); submit-booking gained a Deno test for the
  server-side past-date rejection. 81 React + 35 Deno = 116/116 passing.
- Sept 14, 2026: Dog-profiles reorg (follow-up to v1.5.14's multi-dog
  pricing). New schema: owners (by phone) -> dogs (always-current
  profile) -> stays (one per booking) <- stay_dogs (join; which dogs
  were on a stay, each with its OWN frozen snapshot of that dog's
  profile as declared/signed for that specific booking, kept deliberately
  separate from `dogs` so a later booking's profile update doesn't rewrite
  history - see the migration file for the full rationale). The old flat
  `stays` table is kept as `stays_legacy` for reference and was backfilled
  into the new tables (owners/dogs matched by phone / case-insensitive
  name, one dog per legacy row since that's all the old data had).
  Booking form (Step 2): now collects a full profile - breed/DOB/spay-
  neuter/aggression/health - for EVERY dog on the booking, not just the
  primary one; one repeated block per dog, driven by "Number of Dogs".
  Owner info and the vet are asked once, not per dog, per scope decision.
  Returning-client lookup now autofills the vet plus every known dog,
  growing the dog-block count to match rather than only filling slot 0.
  New submit-booking Edge Function handles the actual write: find-or-
  create the owner by phone and each dog by (owner, case-insensitive
  name), so a returning dog's profile gets updated in place rather than
  duplicated. This is a schema-level architecture change, not just a UI
  one - anon has zero access (not even INSERT) to any of the four new
  tables, since the find-or-create logic needs a SELECT anon was never
  granted; the client-side `supabase.from('stays').insert(...)` call
  from v1.5 is gone entirely, replaced by this one Edge Function call.
  Also slipped in for free since the write path was already being
  touched: client_timezone is now captured and stored per stay (closes
  the old item 5, "signature timestamp - add client timezone").
  Admin panel: now browses by dog (each with its current profile and
  full stay history) rather than grouping flat stay rows client-side;
  each past stay in the history still shows exactly what was declared/
  signed at the time, even if the dog's profile has since been updated.
  Tests: 9 new Deno tests for submit-booking's find-or-create logic
  (new owner+dog, returning owner, returning dog matched case-
  insensitively, multi-dog bookings, the frozen-snapshot behavior) using
  a lightweight in-memory PostgREST stand-in; admin-data and lookup-
  client rewritten with their own new Deno test suites (34 Deno total,
  up from 15). React side: StepDog rewritten for repeatable per-dog
  blocks, AdminView rewritten for the dog-centric response shape, 2 new
  tests for multi-dog-on-mount autofill (75 React total, up from 74).
  109/109 passing.
- v1.5.14: Multi-dog pricing + holiday upcharge (FIXES.txt items 6 & 7).
  calcCost (src/App.js) now computes cost night-by-night: each night is
  checked against getHolidayWindows(year) (algorithmic, not hardcoded —
  New Year's Day, MLK Day, Presidents'/Ski Week [the week containing
  Presidents' Day plus the Sat-Sun surrounding it], Memorial Day, July

  field on Step 2 (About Your Dog) feeds this — v1 scope only collects
  full intake (breed/DOB/vet/etc.) for the primary dog; a

  count for pricing and shows on the admin stay-history view. 26 new
  tests (calcCost multi-dog/holiday cases, isHolidayNight/
  getHolidayWindows unit tests including a different-year check to

  field) — 74/74 passing. Verified live via Playwright against the dev
